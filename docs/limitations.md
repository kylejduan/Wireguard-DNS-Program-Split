# Limitations

- IPv4 only. Selected applications' non-loopback IPv6 is blocked by persistent filters, so they fall back to IPv4 through the tunnel and cannot reach IPv6-only destinations. Unlisted applications keep using IPv6 normally; an IPv6 default route is allowed.
- Ordinary Windows DNS only. Application-owned DoH, DoT, DoQ, raw DNS sockets, and hard-coded IP addresses are payload traffic; they are not rewritten to the profile DNS.
- Exact executable paths only. Child, helper, service, launcher, and updater processes require their own entries.
- Existing connections keep their route until closed, unless Windows re-authorizes them against new filters, which refuses one that is not on the tunnel address.
- The payload filters are persistent WFP objects. A crash of the controller or `wfp-probe.exe`, a BFE restart, a reboot and every repair leave them in place, so selected applications cannot connect, rather than leave directly, until the stack is back. This does not depend on the PIA driver: until it registers its callouts, IPv4 from a selected application has a physical source address and is refused at authorization.
- A VPN provider or server outage blocks selected applications rather than sending them direct: the controller keeps their filters and restarts only the tunnel until tunnel DNS answers again.
- Repairs and reloads never stop the dispatcher, but a dispatcher that crashes or is killed leaves the NRPT rule naming nothing until the supervisor's replacement is ready, about a second later, and all ordinary DNS on the host fails meanwhile rather than letting selected applications' queries reach the physical resolver. If no dispatcher is ready for 15 seconds, the rule is suspended and selected applications' ordinary DNS uses the physical resolver until one is ready again: their DNS queries, and so the names they look up, are then visible to the physical network and its resolver. This is deliberate: keeping DNS working for the rest of the host is judged to outweigh it. Their payload stays blocked or in the tunnel throughout.
- Before BFE starts, only the boot-time copies of the blocks apply. Their enforcement from TCP/IP start has not been observed; confirm it on the deployed workstation.
- An included executable that is absent keeps its filters, keyed by its path; a different program later placed at that path is treated as the included one. An entry whose path does not resolve keeps the filters it already had; one that never resolved has none until it does. Identity is the final path, so every alias of a listed file is covered and the installation root must not itself be an alias.
- The filters own the PIA callout objects persistently. The Private Internet Access desktop client cannot add its own callouts while they exist; do not run both.
- Non-owned NRPT rules for specific namespaces take precedence over the catch-all dispatcher rule. Selected applications resolve those namespaces through whatever server the rule names. The controller logs the namespaces once per distinct set and keeps running.
- An explicit tray disable, `Stop-Service WireGuardProgramSplitController` and uninstallation remove the filters and restore ordinary direct access. While the project is enabled it acts as a per-application kill switch for payload.
- DNS process attribution depends on an undocumented-in-this-project Windows DNS Client ETW event shape and can change in future Windows builds. The controller detects a dead ETW path with an end-to-end probe, but up to one health interval can elapse before repair.
- A query event whose process cannot be identified, typically because it exited before the event was read, may have come from a selected application, so for ten seconds no lookup of that name is routed or answered directly; tunnel evidence still routes to the tunnel, and other lookups of the name are refused meanwhile.
- A missing process hint is fail-closed for that DNS query (`SERVFAIL`), except that a repeat of a name and type answered within the previous three seconds reuses that answer's route. DNS packets and ETW events have no shared transaction identifier, so an unlisted lookup made at the same moment as a selected one for the same name and type may use the tunnel. A selected lookup does not take a direct route decided for the same name: the ordering barrier makes every direct decision wait until the packet's own query event has been processed, and a direct answer is withheld if a selected lookup of the same name started while it was in flight, since the DNS Client would hand it that answer. A selected lookup that starts in the microseconds between that check and the answer's delivery can still receive it. A direct answer already returned may still be in the Windows cache for up to one second. For an answer too large for the client's UDP size, which the dispatcher cannot complete over UDP, the client falls back to TCP, and CI observed the DNS Client service serving a selected application's lookup of a name unlisted processes had just resolved without sending a packet or raising a query event, so the dispatcher never saw it; in 4 to 7 of 20 such rounds per CI run the selected application received the direct answer. For answers that fit, no selected lookup received one in CI: the dispatcher completes them over TCP itself and withholds a direct answer a selected lookup was merged into, which that lookup then sees as a failure to retry. The selected application's traffic to that address is still forced through the tunnel or blocked by its filters.
- DNS response TTLs are zeroed and Windows DNS cache TTL is capped while active. This improves separation but increases query count.
- Dispatcher logs contain queried names, process IDs, and executable paths, are readable only by SYSTEM/Administrators, and rotate automatically at 8 MiB with three archives. Treat retained logs and failure snapshots as sensitive.
- Selected and unlisted applications still share the Windows DNS Client service, loopback dispatcher, host, and administrator trust boundary. This is operational isolation, not a formal security boundary.
- LAN destinations follow the Windows route table. No automatic LAN bypass policy is added. A selected application reaches the LAN only as the PIA redirect leaves it: a socket redirected to the tunnel address follows the tunnel's routes, as before, and a connection the driver leaves on a physical address, including LAN broadcast and multicast from an unredirected socket, is now refused instead of sent directly. Validate it for the intended topology.
- Only one physical default route/DNS source is selected. The controller detects changes every 30 seconds and restarts the stack, so multi-homed, roaming, captive-portal, and rapidly changing adapter setups can experience a short outage and still require live validation.
- Third-party WireGuard DLL and PIA driver compatibility is version-sensitive and outside this project's release process.
