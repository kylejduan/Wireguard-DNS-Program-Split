# Architecture

## Data flow

```text
selected executable ── WFP bind redirect ── WireGuard adapter ── Internet
        │                                        │
        └─ Windows DNS ─ local dispatcher ─ profile DNS

unlisted executable ────────────────────── physical adapter ── Internet
        │                                        │
        └─ Windows DNS ─ local dispatcher ─ adapter/router DNS
```

## Components

- `tunnel-host.exe` exposes a compatible WireGuard tunnel DLL as a Windows service.
- `wfp-probe.exe` manages persistent WFP objects for the exact executable paths in `included-apps.txt`: a fixed project provider with its sublayer, the PIA callout objects, one provider context carrying the tunnel IPv4 address for the signed PIA WFP callout, and per-application filters. `install` deletes every object owned by the provider and adds the new set in one WFP transaction; `verify` succeeds only when exactly that set exists and the PIA driver has registered its callouts; `remove` deletes everything the provider owns. It exits after each operation.
- `dns-dispatcher.exe` listens on loopback port 53. It owns a unique per-launch Microsoft-Windows-DNS-Client ETW session, resolves each event's process path, and binds the upstream query to either the physical or tunnel source address.
- A narrowly owned NRPT `.` rule sends ordinary Windows resolver queries to the dispatcher.
- `controller-service.exe` starts `Controller.ps1` as an automatic SYSTEM service, cooperates with ordered service stop, accepts shutdown and pre-shutdown so that a controller ended by system shutdown is reported as a clean stop, records which path ended it in `controller-service.log`, and lets Service Control Manager restart a failed controller.
- `Controller.ps1` owns startup, recovery, and 30-second tunnel plus end-to-end split-DNS health checks. The controller service is Automatic; the tunnel service is Manual. `Invoke-Tunnel.ps1` serializes stopped-service starts and completes orphan-adapter preflight before starting the host, while adopting a service already Running/StartPending.
- `Tray.ps1`, running as the interactive user, changes the desired state, executable list, and profile.

## Payload filters

Each included executable gets six persistent filters in the project sublayer: PIA callout redirects at the IPv4 bind and connect redirect layers; blocks at the IPv4 connect and receive-accept authorization layers for any local address other than the tunnel address; and blocks at the IPv6 connect and receive-accept authorization layers. Every block spares loopback, which never leaves the host. Selected applications therefore cannot use IPv6, fall back to IPv4, and are bound to the tunnel address. A redirect to that address needs neither the tunnel nor the dispatcher, so the filters are installed before both and stay through every repair: while the tunnel is down, selected applications fail instead of leaving on the physical route. Because the objects are persistent, BFE reloads them after a BFE restart and at boot, before the controller has rebuilt the stack. Each block also has a boot-time copy (`FWPM_FILTER_FLAG_BOOTTIME`), which TCP/IP enforces from its own start until BFE has loaded the persistent set. They are enforced before BFE has loaded the project sublayer, the PIA callouts or the provider context, so the copies are the blocks alone, flagged boot-time instead of persistent, in the default sublayer, under the same provider; install, replacement, verification and removal treat them like the rest of the set. BFE keeps their provider and places them in the universal sublayer, and an enumeration scoped to a layer returns them only with `FWP_FILTER_ENUM_FLAG_INCLUDE_BOOTTIME`, which `wfp-probe.exe` sets. CI proves they are added, verified, replaced and removed, not their enforcement before BFE, which only a reboot of the deployed workstation can show.

An executable in the list that is absent, because it was uninstalled or is being replaced, keeps its filters and produces a warning, logged once per change. Identity follows the final path a running image has, and it is resolved in one place. `wfp-probe.exe install` resolves every listed entry (junctions, symbolic links, substituted drives and short names for a present file; an absent one through its nearest existing ancestor) and records the result in `state\resolved-identities.tsv` after the filters commit. The dispatcher reads that record and attributes by it without resolving again; validation fails unless the copy the dispatcher last loaded, the record and the installed filters agree, and a reinstall that changes the record has the running dispatcher reload it. Resolution never climbs past something that exists: a link or junction whose target cannot be opened, an inaccessible component or an unavailable volume leaves the entry unresolved, and it keeps its recorded identity. `FwpmGetAppIdFromFileName0` needs the file, so for an absent path `wfp-probe.exe` derives the same identifier from that ancestor's NT final path, with ASCII letters lowercased as WFP does, and a terminating NUL. Each filter also carries its listed entry and attribution path as provider data, so an installation without a record still keeps the identifiers and the dispatcher's path of an entry that does not resolve; an entry with identifiers but no path is refused rather than attributed by nothing. CI checks that a restored executable is refused at once and that its identifier matches. The management API lowercases only ASCII letters, while a running image is matched with every letter lowercased: CI showed a listed executable with uppercase non-ASCII letters in its name passing every filter. Each such path therefore also gets the set under its fully lowercased identifier, and CI shows that copy refused. CI covers a junction alias present, absent and restored, a symbolic link whose target is temporarily absent, a junction whose target is unavailable, and a substituted drive removed and restored, including a dispatcher started while it was gone whose selected DNS still goes to the tunnel lane. An entry that does not resolve keeps the identifiers of its committed filters and of the record together, each with the attribution path it had, since an install can stop between committing the filters and publishing the record; the record then holds a line per path and each path's filters carry it, so DNS from either identity is attributed. An entry that never resolved has no filters until it does. `wfp-probe.exe` enumerates only objects of the project provider, and for filters and callouts only on the layers it uses; removal also searches every layer.

Fail-closed does not depend on the PIA driver. The redirect layers only modify a bind or connect, and a callout the driver has not registered (early boot, a stopped, crashed or unloaded driver) lets it through unmodified, as the CI live test observes without the driver. The IPv4 blocks catch exactly that case: both redirect layers are classified before connect and receive-accept authorization, so a redirected socket reaches authorization with the tunnel address as its local address and is not matched, while an unredirected one carries a physical address and is refused. Re-authorization of an existing flow sees the same local address. The condition is the tunnel address from the profile rather than the tunnel interface, because the interface index changes whenever the adapter is recreated and the address does not. The blocks clear the action right and sit in a sublayer of the maximum weight, so no filter or callout of another provider in a lower sublayer can turn them into a permit. They match only the listed executables; `wfp-probe.exe` refuses to list a program installed beside it, which keeps the dispatcher, tunnel host and controller host outside them. The controller still starts the driver before reporting the stack active and reinstalls the filters when verification finds the callouts unregistered.

Only an explicit tray disable, a controller service stop and `Uninstall.ps1` remove the filters. A profile import keeps them through its disable and replaces them with the new tunnel address. It stops only the tunnel: the dispatcher, the NRPT rule and the cache policy stay, so selected applications' DNS keeps failing closed during the swap, and the dispatcher takes the new tunnel address and resolver in place when the stack starts again. An included-application reload is one transactional replacement. Ordinary system shutdown leaves them in place.

## Route invariant

The physical default route must remain Windows' preferred default. The WireGuard adapter receives a deliberately losing default route with metric `9999`; the WFP bind redirect causes selected sockets to use the tunnel source address and therefore its route. The WireGuard endpoint receives an explicit physical `/32` route.

Because unlisted payload does not traverse a universal TUN or user-mode packet engine, direct-path throughput is limited by the normal Windows network stack rather than this project's classifier.

## DNS attribution

Windows commonly performs application DNS through the shared DNS Client service. The dispatcher therefore cannot classify the loopback packet's owner. It pairs the query with the DNS Client ETW event, whose process ID identifies the originating executable.

Measured on the reference workstation on September 17, 2026, 200 paired lookups of common names through the dispatcher matched direct queries to the router at the median (+0.04 ms), with +2.3 ms at p90 and +7 ms at p99 and no failures; PowerShell's per-call cost set a floor of about 10 ms on both paths.

A selected hint chooses tunnel DNS at once. Every other decision waits for an ordering barrier: the DNS Client logs its query event (3006) in the calling process before the query reaches the DNS Client service and is sent to the dispatcher, and the session writes all events to one buffer sequence in logging order (`EVENT_TRACE_NO_PER_PROCESSOR_BUFFERING`). After a packet arrives, the dispatcher writes a sentinel event carrying a sequence number through its own provider on the same session, requests a flush, and waits until its consumer has processed that sentinel and a flush begun after it has checked for lost events. The query event of that packet, if any, has then been seen: tunnel evidence chooses tunnel DNS, else unlisted evidence chooses physical DNS, else the query is refused at once. A barrier that does not complete within 500 ms refuses. In two CI runs every one of 137 forwarded queries arrived 0.2 ms or more after its query event, and physical-DNS decisions including the barrier took 0.46 ms at the median and 0.63 ms at p99. A query that repeats a name and type answered within the previous three seconds, with no newer attribution event, reuses that answer's route: this covers the Windows DNS Client's own retransmissions and TCP fallback, which raise no new event. Any other missing or inaccessible attribution is blocked with `SERVFAIL`. Responses have TTLs zeroed, and the controller temporarily caps the Windows positive cache at one second, reducing cross-process cache reuse.

Selected attribution takes precedence over unlisted evidence for the same name and record type, including an earlier unlisted hint and a reusable direct route. When an upstream UDP answer is truncated, the dispatcher fetches the whole answer over TCP on the route it already chose and returns it over UDP if it fits the size the client advertised (512 bytes without EDNS), so the client does not fall back to TCP. Tunnel evidence also outlasts a newer unlisted event for the reuse window after the selected exchange was answered, because the selected application may still retransmit or fall back to TCP after a truncated answer without a new event, and an exchange's answer finalizes only the evidence it was decided on. DNS packets and ETW events do not share a transaction identifier, so an unlisted lookup made at the same moment as a selected one may be sent to the tunnel. The Windows DNS Client also merges a lookup into an identical one already in flight, so a selected application asking for a name an unlisted one is resolving sends no packet of its own; before delivering a direct answer the dispatcher therefore passes the barrier again and, if a selected query event for the name has arrived, withholds the answer with `SERVFAIL`, and the retries go to the tunnel; CI runs concurrent same-name pairs in both orders, distinguishing the lanes by their answers, and no selected lookup reached the direct lane. See [Limitations](limitations.md).

## Startup

The controller service uses `Automatic` start; the tunnel is `Manual` so orphan-adapter preflight runs before creation. The controller waits for a physical IPv4 default route, adopts an already-running tunnel when available, and polls tunnel DNS until the first successful answer instead of sleeping for a fixed delay. It installs or replaces the persistent payload filters in parallel with the driver and tunnel starts, then has the dispatcher load the identity record they wrote, verifies the filters during the tunnel readiness wait, then enables and validates the dispatcher and NRPT path. Periodic NRPT and dispatcher validation uses a reusable PowerShell worker over anonymous pipes, contained with its probes in a kill-on-close job. Each request reloads inputs; a 45-second deadline, failure, stack stop or shutdown discards the worker. Startup and mutation scripts still use separate processes. Every 30 seconds the controller verifies the payload filters and rechecks NRPT conflicts, executable and port ownership, ETW-backed loopback DNS, tunnel DNS, and the physical interface snapshot; repeated failure restarts the stack with fresh values, keeping the payload filters. A filter mismatch or unregistered callout is repaired by reinstalling the filters alone. A VPN-side failure, where NRPT and dispatcher validation pass but tunnel DNS fails or the tunnel host has stopped, restarts only the tunnel with bounded backoff: the filters, NRPT rule and dispatcher stay in place, so selected applications fail closed for the length of a provider or server outage instead of going direct. A failure that an uplink outage can explain (tunnel DNS, the physical snapshot or the end-to-end dispatcher probe) is held while the physical route, address or resolver is missing; every other invariant failure is repaired even then. Each DNS probe makes up to three attempts inside one check, because a single lost datagram or transient refusal is not a dead tunnel and a restart disrupts DNS until it completes. The dispatcher is never stopped by a repair or reload. It reads its inputs from state files (`state\dns-dispatcher-inputs.txt` with the direct and tunnel sources and resolvers, and the identity record) and reloads them in place when `Invoke-DnsDispatcher.ps1 Start` writes new ones and signals `Global\WireGuardProgramSplitDispatcherReload`. It validates the new inputs before swapping them in, keeps the loaded ones when they are invalid, and publishes copies of what it loaded with a reload generation, which validation compares with the current files. A query keeps the inputs it started with. `controller-service.exe` supervises the dispatcher on its own thread, which never waits on the PowerShell controller's blocking work (tunnel readiness, health probes, repairs). While the stack is enabled (`state\dns-dispatcher.supervised`) it adopts the running dispatcher or starts one, and starts another about a second after one ends. A dispatcher survives a restart of the service host and is adopted. If no ready dispatcher has answered for 15 seconds, the supervisor suspends the owned NRPT rule so the rest of the host keeps DNS, recording `state\nrpt-suspended`, and restores the rule once a dispatcher is ready again. Ready means the supervised process published its inputs and answers a liveness query its receive loop handles itself, without attribution or an upstream; a process that exists but stops answering three probes a second apart is ended and replaced, as is one that has not published its inputs ten seconds after it was started or adopted. CI shows both for suspended dispatchers, including one adopted by a restarted supervisor. The same liveness query is part of NRPT readiness and dispatcher validation. It compares the rule's actual state with readiness on every pass rather than acting once per outage, runs the NRPT helper beside the loop so a slow PowerShell start never delays a restart, retries a helper that failed, and republishes the dispatcher's process ID if that record is lost. Enabling the rule also requires a ready owned dispatcher, checked under the NRPT lock; otherwise the rule stays suspended for the supervisor to restore. A reload validates every row of the identity record, so a damaged record is rejected whole rather than deselecting an application; a record with no rows is valid. The invariant: while the stack is enabled, the owned rule names a ready owned dispatcher, except for at most about 15 seconds after the dispatcher ends; only disable, service stop and uninstallation remove the rule otherwise. During those seconds every ordinary lookup on the host fails rather than letting selected applications' queries reach the physical resolver. CI kills the dispatcher at random moments, including during reloads, repairs and health checks, and measures unlisted DNS answering again within about two seconds while selected DNS never takes the direct lane; it also checks reloads under load drop no query, and the suspension and restoration of an owned catch-all rule. If only the tunnel fails to answer during startup, as in a reload during a provider outage, the dispatcher, NRPT rule and filters stay and the tunnel-only restart takes over with its backoff, reporting the stack active once tunnel DNS answers. Disable, service stop and uninstallation remove the rule as before. Before a health-check restart the controller copies the component logs to `logs\health-failures`, since the restart rewrites them.

The controller service reports running as soon as supervision starts, so Service Control Manager is not held pending on network readiness. On service stop it gives ordered cleanup up to four minutes to remove the persistent WFP filters before NRPT and the remaining stack, retrying incomplete cleanup for up to 150 seconds; a forced or failed stop is reported as a service failure. An interactive disable whose cleanup cannot complete is recorded in `last-error.txt` and retried with bounded backoff while the controller keeps supervising, because exiting would only make SCM restart it into the same failure. A tunnel service that stays in `StartPending` or `StopPending` cannot accept a stop control. A slow start is left running for the next repair attempt to adopt, but a host that has been starting for more than 90 seconds, or a stop that does not finish within 20 seconds, is reset by terminating only the owned `tunnel-host.exe`; the next repair then starts from a stopped service. System shutdown sends no stop control and leaves the stack in place for boot-time adoption; the host accepts the shutdown notification only so the controller's termination is not reported as a failure. On an unexpected controller exit, SCM restarts supervision while the persistent filters and the last-known-good dispatcher remain available for validation or repair.

## Long-running resource limits

The Windows controller and native service host retain an 8 MiB current log and three archives (`.1` through `.3`). The dispatcher uses the same bounded writer for `dns-dispatcher.log`; stdout is a separate, short readiness log. A pre-existing oversized log is preserved in the first archive until ordinary rotation ages it out. Rotation failures drop diagnostics instead of growing a file past its limit or restarting networking. Child controller stdout/stderr is pumped through the host's bounded writer, so inherited handles cannot pin a growing log. Logs remain administrator-only and may contain sensitive query and application metadata.

DNS attribution retains at most 4,096 name/type entries, with a ten-second lifetime and at most one expiry scan per second. Overflow blocks forwarding for ten seconds after the last dropped event: a lost selected hint must not turn into a direct query. The process-path cache is capped at 2,048 entries; at most 256 DNS workers run concurrently. TCP clients receive a five-second total request-read deadline and at most 64 requests per connection. Upstream TCP connect, send, and receive share one four-second deadline, including partial transfers. The ETW session is filtered at the provider to the query event alone. If ETW reports lost events or buffers, the dispatcher discards every attribution entry without tunnel evidence and refuses direct routes for ten seconds, so neither an earlier nor a later direct hint for the same name can stand in for a lost selected one; tunnel routing continues. ETW flushes immediately when a query requests attribution and retries every 10 ms while attribution is pending; idle maintenance uses a one-second cadence. Socket waits check shutdown every 200 ms; workers drain before their attribution and Winsock state is destroyed.

Health-failure evidence retains ten snapshots with at most 2 MiB per component log. Each copy uses the size observed when it opens the log, so an active writer cannot extend the copy indefinitely. Health, repair, cleanup and adapter-maintenance scheduling use monotonic time, so wall-clock changes cannot delay checks. DNS and WFP component operations are serialized; process-stop waits are bounded.

The two-second supervision pass reads state files, the owned process images, the tunnel service and the owned NRPT rule's registry key; it starts no process. The payload filters are BFE-owned and persistent, so that pass checks only their install marker. Measured on the reference workstation on October 13, 2026, the registry read of the NRPT rule took 0.27 ms against 4.5 ms of wall time and about 4 ms of CPU for `Get-DnsClientNrptRule`, and one `wfp-probe.exe` run cost about 30 ms of wall time and 11 ms of CPU before any filter-engine work, so filter verification runs with the 30-second checks. See [reliability verification](reliability.md) for the tested scope and remaining platform boundaries.
